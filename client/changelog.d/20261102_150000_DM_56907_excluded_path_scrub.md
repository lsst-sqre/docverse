### Backwards-incompatible changes

- `QueueJob.progress` is now typed `BuildProcessingProgress | ExcludedPathScrubProgress | None`, chosen by the job's `kind`. Payloads for every other kind validate exactly as before, so nothing changes at runtime. Type-checked code that reads a `BuildProcessingProgress` field from `job.progress` must now narrow it first, for example with `isinstance(job.progress, BuildProcessingProgress)`.

### New features

- New `JobKind.excluded_path_scrub` for the queue job that `POST /orgs/{org}/projects/{project}/builds/scrub-excluded-paths` starts. The job reports, and unless it is a dry run removes, the excluded cache paths (`docverse.excluded_paths`) already stored in one project's builds.
- New request and response models for that endpoint, exported from `docverse.models`. `ExcludedPathScrubRequest` has one field, `dry_run`, which defaults to `false`. `ExcludedPathScrubAccepted` carries the scrub job's `job_id` and `job_url`. When a scrub is already queued or in progress for the project, the response names that job instead of a new one.
- New progress models for the scrub report, exported from `docverse.models`. `ExcludedPathScrubProgress` is an `excluded_path_scrub` job's `progress`: `dry_run`, the counters `builds_examined`, `builds_affected`, `objects_removed`, `bytes_removed`, `builds_failed` and `builds_skipped`, and a `builds` list of `ExcludedPathScrubBuild` rows. Each row has `build_id`, `build_url`, `edition_slugs`, `entries`, `error` and `skip_reason`. Its `entries` are `ExcludedPathScrubEntry` values, each a build-relative `path` (`.doctrees/`, `.buildinfo`, `sub/.doctrees/`) with an `object_count` and `total_size_bytes`. In a dry run the `*_removed` counters and the rows describe what the scrub would remove. In a real run the counters are what was actually deleted. All three models keep unknown keys (`extra="allow"`), so later additions to the report do not break older clients.
