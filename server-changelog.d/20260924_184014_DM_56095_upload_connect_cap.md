### Bug fixes

- The keeper-sync worker now caps concurrent presigned uploads at `DOCVERSE_KEEPER_SYNC_UPLOAD_CONCURRENCY` (default 32) across every running job, rather than letting every one of the up to 80 in-flight transfers (`DOCVERSE_KEEPER_SYNC_MAX_JOBS` × `DOCVERSE_KEEPER_SYNC_COPY_CONCURRENCY`) PUT at once. The copy client's pool is sized from the cap (42 connections at the default), keeps every connection alive, and holds an idle one open for 60 s instead of httpx's 5 s, so a burst reuses its connections instead of re-dialling R2 per object. LTD downloads likewise go through one S3 client per worker process, its pool sized from the same cap, instead of a new client per build. This fixes the `ConnectTimeout` storm of backfill run `1xes-dmzz-6r4a-96` on 2026-09-24: the copy client kept only 16 connections alive, so with 80 uploads in flight nearly every finished upload's connection was closed, and each closed connection held one of the node's 64 static Cloud NAT ports through a 120 s TIME_WAIT, until the node ran out of ports and the NAT dropped new connections to R2. `DOCVERSE_KEEPER_SYNC_MAX_JOBS` × `DOCVERSE_KEEPER_SYNC_COPY_CONCURRENCY` still bounds the object bodies the sync worker buffers, and so its memory limit, but no longer sizes a connection pool. `docs/keeper-sync-transport.md` covers the cap, the keepalive policy, the shared LTD source client and the NAT evidence, and why 32 is the intended value until the NAT allocation is raised.
