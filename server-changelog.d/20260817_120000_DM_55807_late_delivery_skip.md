### Bug fixes

- A queue job whose `queue_jobs` row a reaper already failed no longer crashes the worker when arq delivers it anyway. All eight queue-job worker functions — `build_processing`, `dashboard_build`, `dashboard_sync`, `git_ref_audit`, `keeper_sync_project`, `keeper_sync_run_discovery`, `lifecycle_eval`, and `publish_edition` — now claim their row through `QueueJobStore.start_if_queued`, the only queued → `in_progress` transition left in the server, instead of `start()`. When the row is no longer `queued` the worker runs no job body, leaves the row exactly as the reaper left it, and returns the arq result `skipped` rather than raising `InvalidJobStateError` into Sentry. Every skip logs one warning, `Skipping late-delivered queue job`, carrying `queue_job_id` (the base32 public id, the same id the jobs API reports), `queue_job_kind`, and `queue_job_status` — that message is what an operator should grep when a job appears to have quietly done nothing. This closes the residual reap/deliver race the new abandoned sweep opens: the sweep asks arq whether it still knows a queued job before failing its row, but a job re-appearing after that check can still reach a worker, and paging for a race the reaper is designed to absorb is noise. `QueueJobStore.start()` keeps its raising semantics for callers that genuinely require a queued row.
- The two non-`queued` cases stay distinguishable. A terminal row (`failed`, `cancelled`, `completed`, or `completed_with_errors`) is expected reap fallout and is log-only. An `in_progress` row instead means arq re-delivered a job a worker had already picked up — what worker death or a routine SIGTERM pod rotation looks like to the next delivery, since the default pool runs with `retry_jobs=True` and no `max_tries` cap. The body still must not run twice, so the row is still skipped, but the skip also captures a warning-level Sentry event titled "Queue job re-delivered while already in progress", tagged with `job_function` and `job_current_state` and carrying a `queue_job_late_delivery` context with the job's public id. The title is constant so the event groups by kind rather than opening a fresh issue per delivery, which makes a crash-looping worker visible immediately instead of hours later when the reaper notices.
