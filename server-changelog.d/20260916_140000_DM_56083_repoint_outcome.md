### Bug fixes

- The no-op answer to an operator repointing an edition at the build it already serves is now decided while that edition's row is locked. `EditionStore.set_current_build` reports three outcomes — repointed, refused by a guard, and unchanged because the target was already current — instead of deciding "already current" from a read the service took before the lock. Two operators reacting to the same incident (one rolling back to A, one re-requesting the B the edition was serving) could otherwise both be told their postcondition held, while the edition ended on A and the second request's `200` named a build it no longer served. Such a request now waits for the repoint in flight and answers on what it finds: a real repoint, with the history row and publish job that go with one.
- Re-requesting the build an edition already serves works again as the retry for a **failed** publish. `PATCH .../editions/{edition}` with the current `build`, and `POST .../rollback` to the build being served, are inert only while the publish is settled (`pending`, `publishing`, or `published`); with the pair `failed` they record a history row, return the edition to `pending`, and enqueue the `publish_edition` job. Nothing else re-drives such a pair — the reconcile worker leaves it alone by design, keeper-sync's self-heal skips it, and there is no republish endpoint. The project's `date_updated` still does not move, because the build being served has not changed.

### Other changes

- A `PATCH .../editions/{edition}` carrying only `build` no longer runs the edition metadata write, which had nothing to write but still cost a select, a flush, a refresh, and a re-read while the transaction held the project, edition, and build rows. A payload combining `build` with metadata fields still applies both, override first. The build override and rollback also now share one implementation of the repoint-and-publish sequence they had been carrying in duplicate.
