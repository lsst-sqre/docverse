### Bug fixes

- The keeper-sync build content copier no longer lets a large build prefix or a failing key drive the sync worker's memory, which had been OOM-killing it (`Exit Code: 137`) in normal operation and stranding whole project syncs. `copy_build` and `compute_manifest_hash` previously built one coroutine per key and handed the whole batch to `asyncio.gather`, throttling only the downloads with an `asyncio.Semaphore`: a prefix with thousands of keys allocated thousands of pending tasks before any work started, and because `gather` does not cancel its siblings, the first `AccessDenied` propagated to the caller while every other download kept running and kept holding its buffer. A project whose oldest builds fail on every pass therefore leaked one entire fan-out per failed build, all of them live at once. Both methods now feed keys through a fixed pool of at most `max_concurrent` worker tasks pulling from one shared iterator inside an `asyncio.TaskGroup`, so live tasks and buffered object bodies are both a function of the pool size rather than the key count, and the first failing key cancels its siblings before the error is re-raised unchanged to the caller. Keys whose path relative to the source prefix contains a `..` segment are now rejected up front, before any worker starts, instead of part-way through the copy. Each OOM kill had left its job stuck `in_progress` until the 6 h reaper closed it out, and the active-job unique index made the hourly tier cron skip that project in the meantime — so this also removes a silent up-to-six-hour hole in sync coverage per affected project.
