### Bug fixes

- Cloudflare cache purges are now retried instead of being lost to rate limiting. Publishing a release fans out into several purges (the release plus its semver aggregate editions), and a bulk import pushed that burst past Cloudflare's purge rate limit: the API answered `429` with error code `1134` ("Unable to purge, rate limit reached"), the best-effort publish path swallowed it, and the edition went on serving a stale copy at the edge until some later publish happened to purge the same hostname. `CloudflareCachePurger` now retries `429`, the transient 5xx family, and transient transport failures (timeouts, dropped connections) with bounded exponential backoff, honouring a numeric `Retry-After` when Cloudflare sends one but capping any single wait at 10 seconds — the purge runs inside an open publish transaction while holding the per-hostname coalescer lock, so a server cannot be allowed to pin that for minutes; every other non-2xx (including an unfollowed 3xx redirect) still fails on the first attempt, because a retry cannot fix a bad token or an unknown zone. Cloudflare's `errors[].code` is parsed out of the response body and surfaced in the structured error log and as a Sentry tag, so rate-limit exhaustion is greppable and alertable rather than buried in a logged response body. A purge that exhausts its budget still leaves the edition `published` — a CDN outage must degrade to a stale edge copy, not a failed publish — but the failure is now reported to Sentry with the hostname, zone, status, error code, and attempt count instead of being dropped on the floor.
