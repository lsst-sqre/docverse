### Bug fixes

- The four run-less reapers (`dashboard_build`, `publish_edition`, `build_processing`, `dashboard_sync`) now sweep a third class of stuck row: a `queue_jobs` row that reached `status='queued'` with a non-null `backend_job_id` and was then lost by arq. Neither existing pass could see it — `fail_silent_jobs` requires `in_progress` and `fail_orphaned_jobs` requires `backend_job_id IS NULL` — while the active-job partial unique indexes keep counting it as live work, so one such row wedged its slot permanently. On roundtable-dev this silently froze the documenteer version dashboard: every publish cascade saw an active `dashboard_build` and skipped the enqueue. `QueueJobStore.fail_abandoned_jobs` ages candidates out on the kind's existing silent threshold (`DOCVERSE_<KIND>_REAPER_THRESHOLD_SECONDS`, 30 min for `dashboard_build`) but fails a row only after `QueueBackend.get_job_metadata` confirms arq has no record of it, so a job merely backed up behind a saturated worker pool is never cancelled. Reaped rows carry `errors.type='AbandonedQueueJob'`, distinct from `SilentWorker` and `OrphanedQueueJob`, and the reaper's warning line gains `abandoned_count` plus a `reaped_jobs` list naming the matching sweep and `backend_job_id` for every row it failed. If the queue backend is unreachable the abandoned sweep aborts for that tick with a warning and mutates nothing; the silent and orphan sweeps still run, and the next tick retries. This is the reapers' first dependency beyond the queue-job store, supplied through the existing worker factory.
