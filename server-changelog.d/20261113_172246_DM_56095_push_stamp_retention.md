### New features

- The `keeper_sync_push_check` metrics event has a new `outcome`, `completed`: a pushed ref whose window passed after `tier_main` enqueued the project's sync for it at least once at or after its latest push. `expired` now means that `tier_main` never enqueued a sync for the ref in the window. An enqueue made before the ref's latest push, which restarted its window, does not count for it. Both outcomes report what `tier_main` did, not whether a given upload was synced: `completed` also counts an enqueue for an earlier push's upload that a tick caught only after the latest push, and an `expired` ref's upload may still have been imported by a sync that already held the project's slot, one enqueued for another ref or by the `main` check, or `tier_other`. Both outcomes prune the ref, make no LTD call, and carry `enqueued` false with no `push_lag`. The symbol is appended to the event's Avro enum, so every existing symbol keeps its index, and `outcome` is already an InfluxDB tag, so no Phalanx `influxTags` change is needed (PRD #888).
- `tier_main` records each pushed ref's last enqueue in a second annotation on the project's `keeper_sync_state` row, `github_pushed_refs_enqueued`, which maps the normalized ref to an object of `date_enqueued`, the ISO-8601 time of the last project sync it enqueued for it, and `date_rebuilt`, the LTD `date_rebuilt` that enqueue was for (null for a `new_edition` or an edition LTD has never rebuilt). It is pruned with the ref's stamp, so it holds at most one entry per stamped ref and is bounded by the 20-ref cap on `github_pushed_refs` rather than capped on its own (every ref still stamped keeps its entry), and a missing or malformed map or entry reads as no enqueue, so rows written before it need no migration; an entry holding only a time reads as an enqueue whose rebuild is unknown. With `keeper_sync_push_hot_path_enabled` off it is neither read nor written.
- `edition_published`'s `ltd_lag` and `build_content_copied`'s `ltd_lag_seconds` are now measured on the first import of an edition LTD created after the Docverse project (the LTD edition's `date_created` is later than the project's), so the wait for a new branch's first build to reach Docverse shows up in the lag metrics. That covers a retry of a first import whose copy failed, and the first build of an edition keeper-sync imported before LTD had a build for it. First imports of editions created before the project, the editions a backfill imports, stay null, and rebuilds of mirrored editions are measured as before. Values stay unclamped, and an LTD edition with no `date_rebuilt` still yields null. A known limitation: the rule cannot see a gap in mirroring after the project was created (a project tombstoned and restored, one that left and re-entered the sync scope, a paused organization, or a `lifecycle_preemptive` tombstone cleared without a new rebuild), so the first import of an edition LTD rebuilt during the gap reports a lag that spans it (PRD #888).

### Bug fixes

- The keeper-sync push hot path no longer stops watching a pushed ref once it has enqueued the ref's sync. `tier_main` now keeps the ref's stamp in `github_pushed_refs` until `keeper_sync_push_window_seconds` after its latest push, checking it on every tick, so a later LTD rebuild of the ref inside the window enqueues the project's sync again. Before, a branch edition could take one to two hours to reach Docverse after LTD rebuilt it, waiting for `tier_other`, in two cases: a new branch whose edition LTD created before the CI upload landed, so the first sync imported it with no build; and several pushes to one ref, where the rebuild from an earlier push's CI run was synced and the stamp of the latest push cleared. A ref can now enqueue its project's sync more than once per window; each enqueue's `push_lag` is measured from the ref's latest push, and an enqueue attempted while a sync of the project holds its slot is skipped and checked again on the next tick, as before. A new LTD rebuild of the ref enqueues at once, but the same rebuild enqueues again only 15 minutes after the ref's last enqueue for it (`PUSHED_REF_REENQUEUE_BACKOFF`, a module constant), so a sync that completes or fails without recording the rebuild (a build copy that keeps failing, or a lifecycle tombstone's review whose GitHub live-refs read failed) re-runs at most four times per rebuild in the default window instead of on every tick. A visit the backoff holds back publishes its `rebuilt` or `new_edition` outcome with `enqueued` false and no `push_lag`, leaves the ref's recorded enqueue untouched, and logs `held_back` true on `Tier-main: checked pushed ref`. The extra LTD load is bounded by one window of five-minute checks per pushed ref (12 at the default one-hour window) and 20 refs per project (PRD #888).
- `keeper_sync_tier_other` now refreshes a non-`main` edition last synced 10 minutes or more ago, down from one hour, while its cron stays hourly. With the threshold equal to the interval, an edition synced any time after a tick was still under an hour old at the next tick and waited for the one after, so a rebuild that no push window watched could take two hours to reach Docverse. A push hot-path sync re-syncs the whole project and so stamps every edition, and on `rubin/dp2` those syncs landed 20 to 25 minutes before the next tick. Now only an edition synced in the last 10 minutes before a tick waits for the one after, so the wait is about 1 h 10 min at worst. A hot project whose non-`main` editions only `tier_other` syncs is now re-synced on nearly every hourly tick rather than every other one. `TIER_OTHER_REFRESH_THRESHOLD` stays a module constant (PRD #888).

### Other changes

- `docs/metrics.md` documents the `completed` outcome, repeated enqueues, their `push_lag` and the per-rebuild backoff, the revised `expired` and what neither closing outcome proves, and the first-import rule for `ltd_lag` and `ltd_lag_seconds` with its mirroring-gap limitation. `docs/github-integration.md` describes the stamps kept until the window closes, the `github_pushed_refs_enqueued` map and the per-rebuild backoff it drives, and the 10-minute `tier_other` threshold, and `docs/keeper-sync-budget.md` and `docs/keeper-sync-transport.md` state the threshold, the push-window polling and per-push sync cost, and the first-import lag rule where they mention them.
