### New features

- Each arq worker now sizes its database connection pool from the concurrency it declares instead of inheriting SQLAlchemy's request-shaped defaults. `worker_db_pool_sizing()` budgets two connections per concurrent job — jobs that take an `EDITION_UPDATE` advisory lock hold a dedicated `engine.connect()` on top of their own session connection — plus five spare for cron and reaper work, and each pool's `on_startup` passes the result to `db_session_dependency.initialize`. At the stock `max_jobs = 10` the old `pool_size=5, max_overflow=10` left five slots for ten session checkouts, so keeper-sync jobs blocked out `pool_timeout` and raised; `sync_project`'s per-edition `except Exception` then laundered each into an edition failure that could trip the systemic-abort or consecutive-failure breakers.
- `publish_edition` is registered with an explicit per-job timeout, `DOCVERSE_PUBLISH_EDITION_JOB_TIMEOUT_SECONDS` (default 1800 s), replacing arq's implicit 300 s default. It is the default pool's one deliberate sleeper — it waits on the `EDITION_UPDATE` lock, the per-hostname CDN purge coalescer, and the purger's rate-limit backoff — and none of those waits were reflected in the inherited budget. The value sits well below `publish_edition_reaper_threshold_seconds` so the cron backstop never fires on a job arq is still running. `max_tries` is deliberately left unset, preserving the retry policy the job already had.

### Bug fixes

- `publish_edition` no longer runs the CDN cache purge inside its `EDITION_UPDATE` advisory lock. `LockService.acquire` pins a dedicated connection for its whole block, so a publish sitting in the purger's Cloudflare 429 backoff (up to three waits clamped to 10 s) held a pool connection the purge never touches — and, because keeper-sync takes the same lock key in `sync_build` and `_ensure_aggregate_edition`, parked the sync worker's next import of that edition behind the backoff. The purge (and the coalescer wait it queues on) now runs after the lock is released, matching what `purge_cdn_cache`'s docstring already promised.
- A `publish_edition` job cancelled during its CDN purge no longer strands a committed publish as `in_progress`. The `queue_jobs` completion is now committed before the purge, so a timeout cancellation — which is a `BaseException` and escapes `purge_cdn_cache`'s best-effort `except Exception` — costs only the best-effort purge instead of leaving a successful publish for `publish_edition_reaper` to fail up to four hours later.
