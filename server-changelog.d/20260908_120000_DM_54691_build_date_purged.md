### New features

- Builds carry a `date_purged` timestamp, reported on every build response alongside `date_created`, `date_uploaded` and `date_completed`. It records when a soft-deleted build's object-store content was permanently reclaimed, and it is what separates a build that can still be restored from one whose files are gone: null means the content is still there, a timestamp means the row is a tombstone. The `purgatory_cleanup` sweep released alongside it is the only writer, so every build that predates its first run reads null: no existing build is backfilled, because a backfill would declare objects reclaimed while the bytes were still on the store.

### Other changes

- A new migration (`c4d5e6f7a8b9`) adds `builds.date_purged` along with the two partial indexes the purgatory sweep runs on: `idx_builds_purgatory`, the reap-pending work list over `builds (date_deleted) WHERE date_deleted IS NOT NULL AND date_purged IS NULL`, and `idx_queue_jobs_purgatory_cleanup_active_uq`, the per-org mutex over `queue_jobs (org_id) WHERE kind = 'purgatory_cleanup' AND status IN ('queued', 'in_progress')` that mirrors the existing `lifecycle_eval` and `git_ref_audit` mutexes. Builds already soft-deleted when the migration runs are deliberately left unstamped: they are the sweep's first work items, and a backfill would declare their objects reclaimed while the bytes were still on the store.
