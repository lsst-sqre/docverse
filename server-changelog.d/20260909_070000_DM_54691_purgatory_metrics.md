### New features

- The `purgatory_cleanup` sweep now reports itself to Sasquatch. Each per-org tick publishes one org-scoped `purgatory_cleanup_completed` event after its final commit, carrying `success`, the purged/failed/skipped-referenced build counts, the objects deleted, the bytes reclaimed, whether the per-job cap ended the work list, and the elapsed time. The job keeps no run table and its `queue_jobs` row is itself subject to retention, so this event is the durable record that the sweep ran and what it took back — read against the `resource_inventory` gauge's `purgatory_bytes`, which is the footprint still waiting.
- Every purged build also publishes one `lifecycle_action` event carrying the new `trigger = purgatory_cleanup` and `action = retention_expired`, scoped to the build's project — including a project that has itself been soft-deleted, since the project cascade is what carries most builds into purgatory. Reusing the reapers' event type lets a consumer follow a resource from the rule that retired it through to the sweep that freed its bytes. A reap is published only once the build's `date_purged` stamp has committed, so a build restored mid-purge, or a worker that dies mid-loop, produces no event claiming a retirement the database never recorded.
