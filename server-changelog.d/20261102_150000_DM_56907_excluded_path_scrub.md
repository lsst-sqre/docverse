### New features

- New admin endpoint `POST /orgs/{org}/projects/{project}/builds/scrub-excluded-paths` removes the excluded cache paths that builds ingested before the filter existed. These are the same `docverse.excluded_paths` names the ingest filter now skips: `.doctrees/`, `.buildinfo` and the rest. The body is `{"dry_run": bool}` and defaults to a real scrub. The endpoint returns `202` with a `Location` header and a `job_url` for an `excluded_path_scrub` queue job on the maintenance pool. A project runs at most one scrub at a time, so a request made while one is queued or in progress returns that job instead of queueing another. The job walks the project's completed, non-deleted builds that no earlier scrub has stamped and lists each build's prefix with object sizes. Its `progress` is the scrub report: `dry_run`, the counters `builds_examined`, `builds_affected`, `objects_removed`, `bytes_removed`, `builds_failed` and `builds_skipped`, and one row per affected, skipped or failed build. Each row gives the build's id and URL, the editions serving it, and each excluded entry (`.doctrees/`, `.buildinfo`, `sub/.doctrees/`) with its object count and bytes. The report is rewritten as the job runs, so a long scrub can be read before it finishes. A dry run deletes nothing and writes no build row.
- With `dry_run` false, the scrub deletes each affected build's excluded objects. It then subtracts the deleted objects and bytes from the build's `object_count` and `total_size_bytes` and stamps the build's `excluded_paths_scrubbed` annotation with the date and what was removed. The next inventory census's `total_build_bytes` drops by the same amount. The build's `content_hash` is left as it was ingested, because keeper-sync's state short-circuit, not the hash, is what keeps an unchanged LTD build from being copied again. A build that is deleted, retired, or finished by another scrub after the job lists it is skipped and reported with a `skip_reason`. A build whose listing, deletes, or inventory write fails gets an `error` on its row and stays unstamped, and the job goes on to the next build and ends `completed_with_errors`. Stamped builds are not listed again, so a re-run touches only the builds an earlier run did not finish, and a second run of a clean project reports no affected builds.
- Added `excluded_path_scrub_reaper`, the cron backstop for the scrub, on the maintenance pool at minutes 27 and 57. It sweeps `excluded_path_scrub` queue jobs on the shared run-less reaper, as `purgatory_cleanup_reaper` does for the purgatory sweep. It fails a row left `in_progress` longer than `DOCVERSE_EXCLUDED_PATH_SCRUB_REAPER_THRESHOLD_SECONDS` (six hours by default) by a worker that died mid-scrub, a `queued` row whose enqueue never reached arq, and a `queued` row arq lost, after checking that row against the queue backend. Without it, the scrub endpoint would keep answering every request for that project with the dead job. The reaper changes only the queue row: builds the dead job finished keep their stamps and corrected inventory, and the next scrub resumes with the rest.
- Each finished scrub publishes one project-scoped `excluded_path_scrub_completed` metrics event after its queue row's final commit. The event carries `dry_run`, the report's counters (`builds_examined`, `builds_affected`, `objects_removed`, `bytes_removed`, `builds_failed`, `builds_skipped`), and the elapsed time. The report's queue row is subject to retention, so the event is the lasting record of what a scrub found or removed. A scrub that fails outright or is cancelled publishes nothing.
