### Bug fixes

- Builds synced from LTD no longer import the zero-byte "directory marker" objects LTD's uploader writes alongside a build's real files (`<prefix>/_static`, `<prefix>/_sources`, `<prefix>/_images`, …; every Sphinx build in the bucket carries several). Docverse serves nothing from them, and a client tarball of the same tree cannot contain them at all — a file and a directory cannot share a name, and the build-processing worker already skips non-file tar members — so hashing them made a keeper-synced build and a byte-identical client upload disagree on their content identity. Dual-upload convergence therefore only ever fired for builds with no subdirectories. A build synced after this release drops the markers before hashing and copying, so `content_hash`, `object_count`, and `total_size_bytes` all change for any marker-bearing prefix, and the destination no longer holds marker objects. Historical rows are not backfilled (forward-only, consistent with the content-identity change in this same release), so a previously synced build converges with a client upload of the same content only once LTD republishes it. One consequence for the edition-prefix fallback used when a build prefix answers `AccessDenied`: an edition prefix holding nothing but markers now reads as "nothing recovered" and the denial is re-raised, leaving the edition retryable, where before it would have imported a build whose only objects were markers.
