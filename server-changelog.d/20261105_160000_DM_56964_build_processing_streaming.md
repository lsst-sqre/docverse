### Backwards-incompatible changes

- The worker now needs a writable, disk-backed temporary directory (Python's `TMPDIR`, else `/tmp`): `build_processing` spools each build's staging tarball to a temporary file there instead of holding it in memory. A deployment that runs the worker with a read-only root filesystem, as the Phalanx chart does, must mount an `emptyDir` volume at `/tmp` (not `medium: Memory`, which would count the tarball against the memory limit again) before upgrading, or the default-pool worker, which runs `build_processing`, fails at startup: it now checks that it can create the file there before it takes any job. The volume needs room for the largest tarball for each `build_processing` job that can run at once.

### Bug fixes

- `build_processing` no longer holds a whole build in memory. It held the downloaded tarball and every extracted file at once before its first upload, so a pipelines weekly (8,598 files, 390 MB, a 94 MB tarball) OOM-killed the worker at its 1Gi limit 40 s into the unpack, leaving the job `in_progress` for arq's full job timeout. The tarball is now streamed to a temporary file and read back in stream mode one member at a time: the job takes a slot of its upload window before it reads a member's bytes and uploads the member at once, so at most `keeper_sync_upload_concurrency` files are in memory per job. The temporary file is removed whether the job completes, fails, or is cancelled. The first failed upload now also stops the unpack and cancels the job's other uploads instead of leaving them running after the job has failed, and the store's own error is still what reaches Sentry. A build's `object_count`, `total_size_bytes`, `content_hash` and manifest are unchanged for the same tarball. The `Upload complete` log line gains `tarball_size_bytes`, and `docs/build-processing.md` has a new "Worker memory and disk" section on sizing the worker's memory (the Phalanx `workerResources` value) and temporary disk.
