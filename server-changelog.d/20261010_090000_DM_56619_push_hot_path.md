### New features

- Keeper-sync now uses GitHub `push` deliveries to poll a project on a fast path, so a contributor's branch or tag edition reaches Docverse within a five-minute `tier_main` tick of its LTD Keeper build, instead of waiting for the hourly `tier_other` cadence or a dormant project's daily one (PRD #803).
  - A signed `push` for a branch or tag stamps the normalized ref, with the time Docverse received the delivery, into the `github_pushed_refs` annotation of every LTD-synced project bound to the repository whose organization has keeper-sync enabled, whose slug is in scope, and which has a live project state row. A repeated push to the same ref moves its time forward. The step runs after the dashboard-template step, in a transaction of its own, never calls GitHub, and never fails the delivery. `github_webhook_received` gains a nullable `projects_stamped` count.
  - `keeper_sync_tier_main` checks each stamped ref's LTD edition on every tick. Once LTD has rebuilt the edition, or lists one keeper-sync has not seen, it enqueues the project's `keeper_sync_project` through the existing per-project slot and clears the stamp. A ref whose window passes without a rebuild is pruned, and nothing retries it.
  - While a ref is inside the window, the project counts as hot on all three tier crons, so a dormant project a contributor pushes to is also visited by `tier_discovery` and `tier_other` on their fast cadence.
  - New settings `keeper_sync_push_hot_path_enabled` (`DOCVERSE_KEEPER_SYNC_PUSH_HOT_PATH_ENABLED`, default `true`) and `keeper_sync_push_window_seconds` (`DOCVERSE_KEEPER_SYNC_PUSH_WINDOW_SECONDS`, default `3600`). With the hot path off, a push stamps nothing and `tier_main` makes exactly the LTD calls it made before.
  - New `keeper_sync_push_check` metrics event, one per stamped ref each `tier_main` tick visits: `github_ref`, `outcome` (`new_edition`, `rebuilt`, `unchanged`, `expired`, `not_found`, or `error`), `enqueued`, and `push_lag`, the time from the push to the enqueue of the project's sync, set only when the visit enqueued one. It is tagged by `organization`, `project`, and `outcome`, all already on the Phalanx `influxTags` list, so it needs no change to that list. `github_ref` is a field, because branch names would grow a series per branch as a tag. A failed publish is logged and sent to Sentry and never stops the tick.
  - `GET /orgs/{org}/keeper-sync/projects/{ltd_slug}`, and each entry of `GET /orgs/{org}/keeper-sync/projects`, gain `pushed_refs`, the project's stamps newest first, each with its `git_ref`, `date_pushed`, and whether it is still `in_window`, and `in_push_window`, whether any stamp holds the project on the fast path. While it does, every `tier_status` entry reads `"cohort": "hot"`.

### Other changes

- `docs/github-integration.md` has a new section on the keeper-sync push hot path: the stamp, the window, how a push counts as hot, the `tier_main` check and its outcomes, its log lines and metrics event, the switch, and where to read a push. `docs/metrics.md` documents `keeper_sync_push_check` with an example InfluxQL query for its catch rate and `push_lag`.
