### New features

- A new built-in `eups_release` slug rule derives `kind=release` for final three-component EUPS release refs such as `v30_0_12`, so a project like pipelines no longer needs a per-project regex rule to classify its stack releases. It runs after `eups_major` (which still claims two-component tags such as `v17_0`) and before `eups_weekly`. Release candidates (`v30_0_12_rc3`) match no built-in rule and stay `draft`. Keeper-sync imports of LTD `git_refs` editions pick up the same classification, and an existing derived-kind draft such as `v30_0_11` converges to `release` on its next build. The `eups_release` type is also accepted in org/project `slug_rewrite_rules`, so an operator can re-tag final releases with an explicit `edition_kind`.
