### Bug fixes

- The keeper-sync tier crons now run under arq timeouts derived from their own cron intervals instead of arq's 300 s default: 1500 s for `keeper_sync_tier_discovery` (every 30 minutes) and 3000 s for `keeper_sync_tier_other` (hourly), each the interval less a sixth of it, while `keeper_sync_tier_main` (every 5 minutes) keeps 300 s. The timeout bounds a pass, and in the common case keeps one that started late, because the pool was busy at the tick, from running into the same tier's next tick. arq measures it from when a pass starts, not from the tick, so a pass that started late on a saturated pool can still overlap the next one; the per-project active-job slot still allows only one sync job per project, so a project both passes try to enqueue is synced once. On roundtable-prod on 2026-10-06, after `pipelines` (2,938 LTD editions) entered the `rubin` organization's scope, the discovery and other passes reached the 300 s default on every tick, and the projects at the tail of the scope were never visited. A cancelled pass now logs one `Keeper-sync tier pass cancelled` warning with the tier, the inferred `reason` (`job_timeout` or `worker_shutdown`), how long it ran, the organizations it finished, and how far it got through the in-flight organization's scope. A project job the pass was handing to arq when it was cancelled is failed with its cancellation read against the tier's timeout rather than arq's default. The timeouts are documented in the keeper-sync time budget page.
