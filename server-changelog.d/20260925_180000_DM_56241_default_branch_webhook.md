### New features

- A project's `__main` edition now follows a default-branch rename delivered by GitHub. The `repository` webhook the GitHub App already receives for renames and transfers is now also handled for `action: edited`: when its `changes` carry `default_branch`, every project bound to the repository (matched by `repository.id`, with the `(owner, name)` fallback for projects whose id is unresolved) records the new branch in `github.default_branch`, and a `__main` in `git_ref` mode that still tracks the old default branch is rewritten to track the new one. In the same transaction the `main`-style draft edition that tracking auto-created on the new branch is soft-deleted and unpublished, and `__main` is repointed at the new branch's newest completed build (subject to the usual stale-build guard), which queues its `publish_edition` job and moves the project's `date_updated`. Each project whose `__main` was rewritten gets one `dashboard_build` and one `edition_lifecycle` `update` event, as a `PATCH` of the edition would. A `__main` tracking any other branch or tag, or in `lsst_doc` mode, is left alone and only the column is written; only the tracked ref changes, never `kind`, `title`, or `lifecycle_exempt`; and a redelivery is inert. Edits that do not change the default branch, and repositories no project is bound to, are logged and ignored. The `github_webhook_received` event's `jobs_enqueued` counts the `publish_edition` and `dashboard_build` jobs such a delivery enqueues. No GitHub App or Phalanx change is needed.
