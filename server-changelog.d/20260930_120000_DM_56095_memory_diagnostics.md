### New features

- Every Docverse process now includes an opt-in memory sampler: the API and all three arq worker pools. It lets an operator locate a leak from pod logs in containers that no profiler can attach to. Five settings control it, and all are off or neutral by default:
  - `DOCVERSE_MEMORY_DIAGNOSTICS_ENABLED` (default `false`) starts the sampler. It logs `Memory diagnostics enabled` at startup and then a `Memory sample` line every `DOCVERSE_MEMORY_DIAGNOSTICS_INTERVAL_SECONDS` (default `60`). Each line carries the process's `component` label (`api`, `worker`, `worker-keeper-sync` or `worker-maintenance`), `rss_bytes`, `rss_peak_bytes` and `gc_counts`.
  - `DOCVERSE_MEMORY_DIAGNOSTICS_TRACEMALLOC_ENABLED` (default `false`) adds tracemalloc to each line: `gc_objects`, `tracemalloc_current_bytes`, `tracemalloc_peak_bytes`, and `top_sites`. `top_sites` lists the `DOCVERSE_MEMORY_DIAGNOSTICS_TOP_N` (default `10`) allocation sites whose traced size changed most since the previous sample, recorded at a traceback depth of `DOCVERSE_MEMORY_DIAGNOSTICS_TRACEMALLOC_FRAMES` (default `5`). Tracing roughly doubles the Python heap's memory overhead and slows every allocation, so it is for development environments only. If this setting is on without `DOCVERSE_MEMORY_DIAGNOSTICS_ENABLED`, the process logs a warning and nothing is traced.
  - A sample that fails logs a warning, and the next one still runs. The sampler never holds up startup or shutdown, and it adds no runtime dependency. The Phalanx chart values under `config.memoryDiagnostics` come in a separate Phalanx change.

### Bug fixes

- Each Docverse process now creates one aiobotocore session at startup and opens every S3 client from it. Before, each object store created its own session. The keeper-sync copier builds an R2 destination store for every build copy and every manifest hash, so a backfill created thousands of sessions. Each new session parsed botocore's multi-megabyte S3 service model and endpoint ruleset again, and that churn is a suspect in the sync worker's unbounded memory growth and its OOM kill at 2 Gi during a `ts-*` backfill on roundtable-prod (#751). The worker's shared LTD source client and every destination store now use the one session. `S3ObjectStore` and `LtdS3Source` instances constructed without a session still create their own.
- Each Docverse worker process now keeps its object-store clients open for its lifetime, one per organization, service and upload flavour, instead of opening and closing a client for every build copy, manifest hash and job. Each client built an aiohttp connector and an SSL context loaded with the full CA store, and on roundtable-dev each one left about 2.7 MB of resident memory behind that tracemalloc never saw: the sync worker grew from 194 MB to 1019 MB over about 300 copies even with the shared session (#751). The keeper-sync copier's store, with its own upload budget, copy client and upload limiter, keeps a client separate from the one other jobs use, so a worker holds at most two clients for each organization's object-store service. Every use still reads the service and decrypts its credential, and an edited service or rotated credential replaces the client on its next use. Worker shutdown closes every client. The worker logs `Opened shared object store client` and `Replaced shared object store client` with an `open_clients` count. The API process is unchanged and still opens and closes a client per request.

### Other changes

- New page, `docs/memory-diagnostics.md`, linked from `docs/index.md` under Operations. It covers what each `Memory sample` field means, the five settings and their Phalanx values, and how to turn the sampler on for roundtable-dev. It also explains how to tell Python-heap growth (the traced size tracks RSS) from fragmentation or native memory (RSS far above the traced size), when to try `MALLOC_ARENA_MAX=2`, how to read `top_sites` from one tick to the next, and why tracemalloc stays in development environments. A "Shared destination clients" section explains the worker's client cache and the log lines that count its clients. `tests/docs_test.py` fails if the page stops matching the settings, the sampler's or the cache's log lines, or the fields a `Memory sample` line carries.
