### New features

- The daily `git_ref_audit` now keeps each GitHub-bound project's `__main` edition on the repository's default branch without a webhook. Alongside the live ref set it already fetches, it reads `GET /repos/{owner}/{repo}` for each project (with the App installation's token, or anonymously for projects with no installation) and records `github.default_branch`, which backfills the column on every existing project within a day of upgrading. When a project's `__main` is in `git_ref` mode and tracks a ref that is missing from the live branches and tags, the audit rewrites it to track the default branch, soft-deletes and unpublishes the duplicate draft on that branch, and repoints `__main` at the branch's newest completed build. This is the same rule the `repository` `edited` webhook applies, so a missed delivery or a project with no App installation still converges. A `__main` that tracks a branch or tag that still exists is never touched. A failed `GET /repos` for one project is logged and does not stop the rest of the organization's pass; that project's `ref_deleted` reaping still runs, and the pass ends `completed_with_errors`. The per-organization "Git ref audit completed for org" log line now reports `default_branch_updates` and `main_rewrites`.
- The `project_github_resolve` worker now records the default branch through the same rule, passing the previously stored value as the old default branch. A first resolve only records the branch. A resolve that finds a different default branch, for example after a project is rebound to another repository, rewrites a `__main` that still tracks the previously recorded branch. Whenever either worker rewrites `__main`, it enqueues a `dashboard_build` and publishes an `edition_lifecycle` `update` event, as the webhook does.
